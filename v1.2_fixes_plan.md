## B-3 — the single-parent invariant

**The rule the engine already assumes:** every item has exactly one parent, either a layer (`layer.items`) or a group (`group.items`). The renderer walks layers → items → group children, so an item listed under two parents is drawn twice. The MCP store enforces this: `addGroup` (`src/mcp/store.ts:1070-1080`) detaches each child from layers and other groups "so the renderer doesn't draw it twice". Three places break it:

| Where | What happens |
|---|---|
| `src/compose/scenes.ts:470-474` | The synthetic wrapper's `groupChildren` is every key of `defItems.items`, so a scene item owned by a scene-internal group is also a direct wrapper child. |
| `src/compose/templates.ts:326, 374, 404` (`expandRootTemplates`) | `expandedIds = Object.keys(expanded.items)` is spliced into the layer, so a child of a template-internal group sits in the layer too. |
| `src/mcp/tools.ts:1786-1795` (`apply_template`) | Every expanded item is added with `layerId`. The store detaches only when a *group* is added after its children, and the loop goes in whatever order the template declares its items. |

Nothing in `src/schema/validator.ts` rejects an item that has two parents, so all three pass `validate`.

**Repro (verified 2026-09-18):**
```ts
templates: { t: { id: "t", params: [], items: { g: { type: "group", items: ["kid"], transform: T }, kid: box }, tweens: [] } },
scenes:    { s: { id: "s", duration: 1, params: [], items: { g: { type: "group", items: ["kid"], transform: T }, kid: box }, tweens: [] } },
layers: [{ id: "L", …, items: ["ti", "si"] }],
items:  { ti: { $template: "t", params: {} }, si: { type: "scene", scene: "s", transform: T } }
// precompile → layer L: ["ti__g", "ti__kid", "si"]   ← ti__kid twice (layer + group)
//              items.si.items: ["si__g", "si__kid"] ← si__kid twice (wrapper + group)
// validateComposition → valid: true
```

**Blast radius:** no shipped template, seed-library template or example scene contains a group (`grep` over `src/compose/builtInTemplates.ts`, `scripts/seed-global-library.ts`, `examples/*/scenes/`). So goldens should not move. Only user or agent content that nests groups in a scene or template changes pixels, and in every such case it changes from wrong to right.

### Session F1 — Compile passes emit only top-level ids to the parent ⚠ pixel-changing (for affected content only)
**Goal:** a scene wrapper's children and a template's layer entries are the definition's *top-level* items only: ids not listed in any group inside the same definition.
**Files:** `src/compose/scenes.ts:370-480` (item loop, `groupChildren`), `src/compose/templates.ts:307-410` (`expandRootTemplates`), `src/compose/templates.ts:451-495` (`expandTemplatesInScene`: no change needed, the scene pass filters afterwards; confirm with a test), `src/compose/repeat.ts` (`replaceGroupRepeatRefs`: group refs to a `$repeat` key are already rewritten to the produced ids, so run the ownership pass *after* that), new `src/compose/ownership.ts`, `tests/compose/`.
**Steps:**
1. New helper `topLevelIds(items: Record<string, unknown>, order: string[]): string[]`. It collects every id listed in any `type: "group"` item's `items` within the given map and returns `order` minus those ids, keeping declaration order. It is pure and has no knowledge of prefixes, so callers pass already-prefixed maps.
2. `expandSceneInstance`: build `groupChildren` from `topLevelIds(items, internalIds-in-declaration-order)` instead of `Object.keys(defItems.items)`. Keep the `$bg` child first. A nested scene instance referenced by an inner group (`group.items: ["child"]` → `inst__child`) is its wrapper id, so the same rule handles it.
3. `expandRootTemplates`: `expandedIds = topLevelIds(expanded.items, Object.keys(expanded.items))`. Note that the `E_DUPLICATE_ID` check must still cover *all* expanded ids, not just top-level ones.
4. Edge case to decide and test: a group inside a scene that lists a `$template` instance key. Today the key is lowered to `lower__*` ids *before* the scene pass, so the group would reference a missing id (`E_ITEM_MISSING`). Keep that as an error but give it a clear message (`E_INVALID_VALUE`: "groups inside a scene can't reference a template instance; list its emitted ids") rather than silently fixing it.
5. Bump `SCENE_EXPANSION_VERSION` 4 → 5 (doc-comment entry in the same style as v1→v4) and add `TEMPLATE_EXPANSION_VERSION = 2` in `templates.ts` (v1 = everything up to now). Add a ⚠ `CHANGELOG.md` entry under `## Unreleased`.
6. Tests: (a) the repro above for both paths: layer gets `["ti__g", "si"]`, wrapper gets `["si__g"]`; (b) paint-count test: render one frame of a scene whose group holds one opaque 10×10 child at 50 % group opacity and check the pixel alpha is 0.5, not 0.75; (c) group → group → leaf nesting inside a scene; (d) `$repeat` children referenced by a scene group; (e) nested scene instance held by a scene group; (f) a template emitting a group, expanded inside a scene.
7. Add **B-3** to `BUGS.md` §2 (new §2.6) with the repro, marked closed by this commit.
**Verify:** baseline + `bun run regenerate:goldens` must produce **no diff** (if one appears, stop: a shipped asset nests groups and the blast-radius claim above is wrong).
**Commit:** `fix!: groups inside scenes/templates own their children — no double paint (B-3)`

### Session F2 — Validator enforces one parent; `apply_template` honours ownership; restore the showcase orrery
**Goal:** the invariant is checked, not just assumed, and the MCP path matches the compile path.
**Files:** `src/schema/validator.ts` (code list near `:45-65`; a parent-walk already exists in `validateInvisibleOpacity` at `:283-315`), `src/mcp/tools.ts:1772-1830` (`apply_template`), `src/mcp/store.ts:1251-1280` (`addRawItem`) and `addRawSubItem` (used by `add_scene_instance` at `tools.ts:2186`), README error table (`:876` region), `examples/showcase-v1.1/build.mjs` (orrery).
**Steps:**
1. New validator **warning** `W_ITEM_MULTI_PARENT`: an item id that appears more than once across all `layer.items` and `group.items`. The message names every parent; `path` points at the second reference. A warning rather than an error, because a hand-written v1.x composition might rely on the duplicate draw and turning that into a hard failure is a breaking change. Record the decision here and flip to an error in the next major. Also cover a group that lists the same child twice.
2. `apply_template`: add `topLevelIds(...)` items with `addRawItem({layerId})` and the rest with `addRawSubItem`. Add group items *after* their children so `addGroup`-style detaching is never needed. Roll back as today.
3. MCP test: `apply_template` with a group-bearing user template (`define_user_template`) → `get_composition` shows the child only under the group; `validate` has no `W_ITEM_MULTI_PARENT`.
4. Editor check: `apply_template` from the Library panel goes through the same tool (`apps/editor/app/services/mcp_bridge.ts`). Run the editor suite, no code change expected. No command shape changes, so no dual-schema update.
5. Showcase: rewrite the orrery back to the natural form (an `arm` group rotating the planet, a nested `moonArm` group for the moon), drop the out-of-box-anchor workaround comment, and re-render with `examples/showcase-v1.1/render.sh`. The moon should orbit the planet with no frozen duplicates (check frames at t = 18.2 and 19.5).
**Verify:** baseline; validate the minimal repro *without* the F1 fix applied (e.g. a hand-written comp listing `kid` in both a layer and a group) → `W_ITEM_MULTI_PARENT`.
**Commit:** `feat: W_ITEM_MULTI_PARENT; apply_template keeps group children out of the layer (B-3 follow-up)`

## B-4 — `$repeat` limits

**Current limits** (`src/compose/repeat.ts:33-35`): `REPEAT_MAX_COUNT = 500` per block, `REPEAT_MAX_DEPTH = 4`, `REPEAT_MAX_NODES = 2000`. Differences from `REPEAT_EXPRESSIONS_DESIGN.md` §4.3:

| Design says | Code does |
|---|---|
| budget is "all `$repeat`s in one compile ≤ 2000" | the budget resets on every `expandRepeatItems` / `expandRepeatTweens` call (`repeat.ts:83, 112`). Root items, root tweens, each template instance, each scene instance and each behavior body get a fresh 2000. |
| error codes `E_REPEAT_COUNT` / `E_REPEAT_BUDGET` | one code, `E_REPEAT_INVALID`, with `details.reason` |
| `list_engine_capabilities` advertises `repeat: { maxCount, budget }` | not advertised |

The limits exist to stop a typo (`count: 50000`) from exhausting the MCP server's memory. The per-block cap of 500 is stricter than that goal needs. A generated item is a few hundred bytes of JSON, so 10,000 items is a few MB, and the showcase compiled 1,385 items in about 0.15 s. Real per-frame use cases need more than 500: a frame counter or per-frame caption at 30 fps is 900 for 30 s and 3,600 for 2 minutes. Any 30 fps clip over 16.7 s hits the current cap.

### Session F3 — One real per-compile budget; drop the separate per-block cap
**Goal:** `count` is limited only by a single per-compile node budget, sized for per-frame use on clips up to a few minutes. The limits are discoverable.
**Files:** `src/compose/repeat.ts:33-35, 83, 112, 225-305, 340-415`, callers `src/compose/precompile.ts`, `src/compose/templates.ts`, `src/compose/scenes.ts`, `src/compose/behaviors.ts` (grep `expandRepeatItems|expandRepeatTweens`), `src/mcp/tools.ts` (`list_engine_capabilities`), `README.md:700-720, 876`, `REPEAT_EXPRESSIONS_DESIGN.md` §4.3, `tests/compose/repeat.test.ts:14, 231, 271`, `examples/showcase-v1.1/build.mjs` (HUD).
**Steps:**
1. Decision: `REPEAT_MAX_NODES = 10_000` **per compile**, and `count` must be an integer in `[0, REPEAT_MAX_NODES]`. The per-block 500 cap goes away because the budget already bounds it. `REPEAT_MAX_DEPTH` stays at 4. Keep `REPEAT_MAX_COUNT` exported as an alias equal to `REPEAT_MAX_NODES` so imports don't break.
2. Make the budget shared: `precompile` creates one `{ nodes: 0 }` budget and threads it through `SubstitutionContext` (or an options field) into every `expandRepeat*` call, including those inside template, scene and behavior expansion. Standalone callers (the MCP `apply_template` / `add_scene_instance` / `apply_behavior` paths) get a fresh budget per tool call, which is the natural unit there. Scene `loop` copies are not `$repeat` nodes and don't count.
3. Error codes: keep `E_REPEAT_INVALID` (renaming it is a breaking change for agents that match on it) and make `details.reason` one of `count` | `budget` | `depth` | `as` | `id`. Update the design doc to match the code rather than the other way round, and note the drift in its changelog section.
4. `list_engine_capabilities` gains `repeat: { maxNodes: 10000, maxDepth: 4 }`. This doesn't change the MCP tool count. Check whether `tests/mcp/` snapshots the capabilities payload and update that.
5. Perf guard test: a root `$repeat` of 10,000 text items with `enter`/`exit` windows must precompile + validate in < 2 s on CI. A render of one frame must not scale with hidden items beyond a cheap window check. If it does, record the number and open a follow-up rather than optimising in this session.
6. Tests: 900 in one block passes; 10,001 in one block fails with `reason: "count"`; two root blocks of 6,000 each fail with `reason: "budget"` (proves the budget is per compile); a template instance and a root block sharing the budget; the existing 500-boundary test is rewritten against the new constant.
7. Showcase: collapse `hudA` + `hudB` back into a single `$repeat` of 900 and re-render. Frames at t = 14.9 and 15.0 (either side of the old 450 split) show `frame 448` and `frame 451`.
8. README: replace "count is 0–500 and one list may produce at most 2000 entries" with the new rule.
**Verify:** baseline + the perf guard + `bun run stats.ts` in the showcase still reports the same item count (1,385).
**Commit:** `feat: $repeat budget is per compile (10k) with no separate per-block cap; limits in list_engine_capabilities (B-4)`

**Considered and deferred:** a render-time token in text (e.g. `"text": "frame {frame}/{frames}"`) would make frame counters a single item instead of N. It is the better long-term answer for counters and timecode, but it adds a new render-time evaluation surface (determinism, editor preview, the dual schema). It deserves its own design note, not a bug-fix session.
