# Davidup v1.1 — Implementation Plan (Claude Code session-granular)

**Source:** the 2026-09-12 five-agent audit of `v1.0.0` (branch `v0.2`, tag `v1.0.0`) — engine/schema/compose, node+browser drivers, MCP+CLI, editor, docs. Findings are summarised in `README.md` § *Known limitations* and cited inline below with file:line. One new bug (**B-1**, video `fit` is a no-op) was reproduced empirically; everything else is a documented limitation or a deferred ledger item (R-#, bug 2.x in `BUGS.md`).
**Granularity rule:** 1 session = 1 Claude Code conversation = 1 task = 1 (or a few) atomic commit(s), ending with the stated verification commands green. If a session balloons, stop, commit what's green, and split the rest into a follow-up session.

## How to run a session

Paste this at the start of each Claude Code session:

> Read `v1.1_implementation_plan.md`, execute **Session N** exactly as written. Read the cited files first. Run the verification commands before declaring done. Commit with the suggested message. Tick the session in the progress tracker.

**Standing traps (apply to every session):**
- **Dual schema trap:** any change to engine/MCP command shapes MUST also update `apps/editor/app/types/commands.ts`, or values get silently stripped.
- **Stale editor snapshot:** after engine changes run `bun install` again before touching `apps/editor` — the editor compiles against a snapshot of the workspace package.
- **Global `davidup` bin runs `dist/`:** `npm run build` after source changes if you test through the CLI.
- **MCP tool count is enforced:** adding a tool means `server.json` + README + `examples/mcp-demo.md` counts, or `tests/mcp/manifest.test.ts` fails.
- **Pixel-changing sessions** (marked ⚠) must: bump `BEHAVIOR_EXPANSION_VERSION` / `SCENE_EXPANSION_VERSION` or add a new driver-level marker, add a `CHANGELOG.md` entry, and run `bun run regenerate:goldens` on this platform (CI regenerates `linux-x64`).
- **Verification baseline** (run at session end unless the session says otherwise):
  ```bash
  bun run typecheck
  bunx vitest run
  cd apps/editor && npm run typecheck && node ace test
  ```

### Session 2 — B-1: video `fit` is a no-op — extract at source aspect, fit at draw ⚠ pixel-changing *(new P1)*
**Goal:** `contain` letterboxes, `cover` crops, `fill` stretches, `none` centres — as `computeFitRects` already promises.
**Repro (verified 2026-09-12):** 320×240 `small.mp4` placed in a 640×320 box; all four `fit` values produced byte-identical, stretched MP4s. Cause: `resolveExtractDimensions` (`src/drivers/node/videoExtract.ts:216-231`) returns the item box, and `buildExtractArgs` emits a bare `scale=W:H` (`videoExtract.ts:295`). By the time `drawVideo` runs, `iw == bw` and `ih == bh`, so `computeFitRects` (`src/engine/render.ts:393-441`) is an identity.
**Files:** `src/drivers/node/videoExtract.ts:216-231, 249-261 (hash), 285-299`; `src/drivers/node/index.ts:409-436` (frame decode → provider reports frame w/h); `src/engine/render.ts:385-441`; `tests/drivers/videoExtract.integration.test.ts`; `tests/engine/video.test.ts`.
**Steps:**
1. Extraction resolution policy: extract at the source's native size when known (`asset.width/height` from ffprobe), capped so that the *longest* side does not exceed the item box's longest side × `max(scaleX, scaleY)` rounded up (avoids 4K PNGs for a 320px inset). Use ffmpeg `scale=W:-2` / `-2:H` (aspect-preserving) — never `W:H`.
2. The cache hash already includes W/H, so old entries simply miss. No migration.
3. The frame provider must report each frame's true `iw/ih` so `computeFitRects` receives the source aspect. Confirm `drawVideo` (`render.ts:307-380`) uses the bitmap's own dimensions, not the item box.
4. Tests: (a) unit — `resolveExtractDimensions` preserves source aspect; (b) integration — the 4-fit repro above renders four *different* files and a pixel probe finds background colour in the `contain` letterbox band and none in `cover`; (c) golden frames regenerate; update `examples/video-*` if their boxes assumed stretching (they use matching aspects, so likely unchanged).
5. Add a driver-level `VIDEO_EXTRACTION_VERSION = 2` export in `videoExtract.ts` and a ⚠ CHANGELOG entry.
**Verify:** baseline + `bun run regenerate:goldens` + eyeball `contain.png` vs `cover.png` from the repro script.
**Commit:** `fix!: video items honour fit — extract at source aspect, letterbox/crop at draw (B-1)`

### Session 6 — Streaming video frame provider (bounded memory)
**Goal:** rendering a 30 s full-frame 1080p clip does not hold ~900 decoded bitmaps in RAM.
**Files:** `src/drivers/node/index.ts:403-436` (comment acknowledges "memory scales with total frames; streaming/LRU is future work"), `src/engine/types.ts:91-108`.
**Steps:** replace eager decode with a sliding window: frames are consumed in monotonically increasing `t`, so keep a window of `[current − 2, current + 16]` decoded per clip, prefetching ahead with a bounded concurrency; `loop: true` wraps the window. Expose `preExtract.maxDecodedFrames` (default 64 per clip). Measure RSS before/after with `examples/video-bg-text` at 1080p in the PR description.
**Verify:** baseline + bitexact test unchanged (same pixels, different residency) + a unit test that the provider never holds more than `maxDecodedFrames`.
**Commit:** `perf: sliding-window video frame decoding, bounded memory`
