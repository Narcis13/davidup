01 — Spec mismatch

The literal line range pointed at the wrong block. The intent was clear; the address was stale.

Proceeded against the real error-mapping code rather than guessing what 208–215 once referred to. The spec's body (preserve issues[], warnings[], add details) only makes sense there.

Resolution

Treat the line range as stale; honour the described intent.

Flagging here so a future maintainer doesn't try to reconcile the address against the current file.

02 — Edit at the source

One envelope, two consumers. Extending it in one place keeps both honest.

Scope decision

Touched src/mcp/errors.ts too, not just the bridge.

MCPErrorBody is the canonical envelope type, defined in the engine. Adding fields only in the editor bridge would have required as any at call sites and left engine-side throws (the MCPToolError path) unable to carry the new context — meaning a tool that already knows the conflicting id could not surface it.

Alternative considered · A parallel EditorMCPErrorBody in the bridge. Rejected — agents consume one wire shape regardless of which path produced the error; two body types would drift.

03 — Field shape

Symmetric for trivial parsing; one escape hatch for everything else.

The new fields

Three new optional fields on MCPErrorBody.

  • issues?: ReadonlyArray<MCPIssue> — validation failures that caused the error. Each row carries message, optional path, optional code. Mirrors both Zod issue shape and the engine validator's ValidationError, so callers can map either source without translation.
  • warnings?: ReadonlyArray<MCPIssue> — non-fatal validator output (e.g. W_TWEEN_TRUNCATED). Same shape as issues on purpose; agents shouldn't need a second parser.
  • details?: Record<string, unknown> — open-ended bag for error-specific context (the conflicting tween id for E_TWEEN_OVERLAP; the rejected name for project-create). Populated opportunistically; agents must tolerate it being absent.
// src/mcp/errors.ts
export interface MCPIssue {
  message: string;
  path?: string;
  code?: string;
}

export interface MCPErrorBody {
  code: MCPErrorCode;
  message: string;
  hint?: string;
  issues?: ReadonlyArray<MCPIssue>;
  warnings?: ReadonlyArray<MCPIssue>;
  details?: Record<string, unknown>;
}
Why · Symmetric issues / warnings shape keeps the consumer trivial; details is the escape hatch for things that don't fit the issue model.

04 — Forward all rows

The headline change. No more [0].

Before / after

Validation errors now forward the full array.

Previously, every validation path flattened to err.issues[0]?.message (or equivalent). Agents would see one issue with no path attribution and had to re-run the validator client-side to discover what else was wrong. After this change, hint keeps its single-line summary for human readers and pre-existing UI surfaces; the new issues / warnings fields carry the whole story.

05 — Same contract everywhere

Argument validation gets the upgrade too.

dispatch.ts

Zod parse failures attach the full issues[] list too.

Without this, the editor bridge would emit rich envelopes for command-level validation but the engine's own argument validation (run before any handler, in both production and tests) would still flatten to a single message. Agents would have to learn which path they hit to know whether issues is present — exactly the inconsistency the spec was trying to remove. 

// src/mcp/dispatch.ts
if (!parsed.success) {
  const issues: MCPIssue[] = parsed.error.issues.map((issue) => ({
    message: issue.message,
    path: issue.path.join("."),
    code: issue.code,
  }));
  return {
    ok: false,
    error: {
      code: "E_INVALID_VALUE",
      message: parsed.error.issues[0]?.message ?? "Invalid arguments.",
      hint: formatIssuePath(parsed.error.issues),
      issues,
    },
  };
}

06 — Backwards compatible

Additive fourth argument. Existing call sites untouched.

MCPToolError

An optional extras arg, not a reorder.

MCPToolError(code, message, hint?) is called from many tool handlers across the engine. Re-ordering positional args or making any of them required would have rippled everywhere. Instead the constructor grew a fourth optional extras object that carries the new fields. toBody() attaches issues / warnings only when non-empty, and details only when defined — so an envelope without extras is byte-identical to before. 

new MCPToolError(
  "E_VALIDATION_FAILED",
  "Composition would fail validation.",
  "Invalid tween at items.foo",
  { issues, warnings, details: { conflictTweenId } },
);

07 — Footgun

The editor reads a Bun-materialised copy of src/, not a live symlink.

Surprise from the existing repo

Edits under src/ need a bun install before apps/editor sees them.

apps/editor depends on the engine via "davidup": "file:../..". Bun materialises that as a real directory at node_modules/.bun/davidup@root/node_modules/davidup — not a symlink. So an edit to src/mcp/errors.ts does not appear under davidup/mcp for the editor until bun install re-syncs the snapshot.

What happened

First typecheck failed with a phantom missing export.

Module '"davidup/mcp"' has no exported member 'MCPIssue'. The export was right there in src/mcp/index.ts, but the editor's TypeScript was reading the stale snapshot. bun install refreshed the snapshot and the error disappeared.

How to apply · After any edit under src/ that the editor imports, run bun install before typechecking or running the dev server inside apps/editor.

08 — Deferred & open

Plumbing landed. Population per tool, and one open question.

Out of scope

Plumbing is in. Each tool can now opt in to populating details.

  • Did not retrofit existing throw sites (e.g. add_tween for E_TWEEN_OVERLAP) to populate details with the conflicting tween id. The fields are reachable now, but only the validation-error paths use them. Each tool would benefit — separate sweep.
  • Did not surface details through the editor UI's error toasts; that surface still reads message / hint only.
Open question

Should details ever appear on success envelopes too?

E.g. for non-fatal warnings on a successful apply. Currently it's error-only. Leaving as-is until there's a concrete need; flagging in case the answer is "yes, and soon".
